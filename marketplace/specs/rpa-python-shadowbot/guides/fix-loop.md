# Failure Fix Loop

## 触发条件

- `pending_fix`、`fatal` 或 `failed`
- `retryable_error` 或 `locked` 重复超过影刀重试策略
- 高频 warning 已影响业务结果
- 业务输出缺失、字段错误或与验收样例不符

## 先收集证据

尽量获取同一 `run_id` 的：

- `input_{run_id}.json`
- `runner_{run_id}.json`
- `logs/run_{run_id}.log`
- `crash_snapshots/crash_{run_id}.json`
- `data/input/` 中的脱敏最小样例
- 错误或缺失的业务输出
- 影刀调用参数和发生步骤

没有证据时先补证据，不直接大范围改代码。

## 阅读顺序

1. runner 结果：确认 status、message、errors、retryable 和任务位置。
2. 日志：确认执行到哪一步、输入摘要和最接近失败的事件。
3. 快照：确认 traceback、异常分类、action、expected、actual 和上下文。
4. 输入与业务输出：验证契约和可复现性。
5. 相关代码、测试和 Git 历史：寻找引入变化的事实。

## 边界分类

| 类别 | 典型表现 | 默认动作 |
| --- | --- | --- |
| 影刀 | 页面、下载、上传、登录、调用参数错误 | 给出影刀调整和复测步骤 |
| 输入契约 | 字段缺失、路径错误、type 未约定 | 修正契约、样例或上游输入 |
| Python | 可用相同输入稳定复现代码错误 | 修改最小代码范围并补测试 |
| 环境 | 依赖、权限、磁盘、编码、路径或配置 | 修复环境并保留诊断信息 |
| 第三方/上游 | 限流、网络、接口或数据源变化 | 重试、降级或通知上游 |

如果项目提供 `fix_target`，先使用它；否则根据证据判断并说明置信度。

## 状态对应动作

- `locked`：检查并发和影刀重试，不先改业务代码。
- `retryable_error`：按策略重试；重复失败后再诊断依赖和幂等性。
- `warning`：通常是业务数据问题；只有分类错误或结果不符合契约时才改代码。
- `pending_fix`：优先检查 Python、规则、环境或依赖。
- `fatal`：优先检查命令参数、输入文件、JSON、基础配置和启动环境。
- `failed`：检查 runner 级异常和是否仍生成了标准结果。

## 修复步骤

1. 构造最小可复现输入。
2. 写出根因和所属边界。
3. 选择最小正确修复，不顺手重构无关模块。
4. 先补能暴露问题的测试，再修复代码；不适合时说明原因。
5. 运行相关测试和完整测试集。
6. 用相同或等价输入执行 runner 回归。
7. 检查业务输出和预期 status。
8. 清理运行产物，保留脱敏 fixture 和必要文档。

## 完成报告

- 原 status 和根因
- 边界分类及证据
- 修改文件和 Git 变化
- 新增或更新的测试
- 测试和 runner 回归结果
- 预期修复后 status
- 影刀或用户仍需完成的手工验证
- 剩余风险

## 禁止事项

- 没有复现或证据就宣称问题已修复。
- 为影刀或上游问题默认修改 Python。
- 修改 runner 协议来掩盖业务错误。
- 把 `SystemException` 转成 success。
- 未经用户确认自动 push、merge 或上线。
